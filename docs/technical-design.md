# DAN-DO：ゴルフスイング解析アプリ 技術設計調査レポート

> Flutter製ゴルフスイング解析アプリの実現可能性調査・アーキテクチャ設計。プランニング時点(2026年時点)でのWeb調査に基づく。

## 0. 結論サマリー(先に正直な評価)

このアプリの技術的ボトルネックは「ボール検出」でも「距離計算の数式」でもなく、**30fps・固定画角・単眼カメラという撮影条件そのものが、インパクト直後のボール(初速40〜70m/s級)を鮮明に捉えられない**という点です。1/30秒のシャッターでは、インパクト直後のボールは数m移動し、フレーム内で強いモーションブラー(線状のstreak)になります。円形として検出できるクリーンなフレームは、実質「アドレス時の静止ボール」と「インパクト直後ごく数フレーム(0.2〜0.5秒程度)」に限られると想定すべきです。

したがって設計方針は、**「動画全編でボールを完璧に追跡する」のではなく、「アドレス時の静止ボール(高精度な基準点)+ インパクト直後の数フレーム(ノイズを含む観測)」から初速・打ち出し角・方向を推定し、そこから先は弾道physicsモデルで延長する」**というハイブリッド方式が現実的です。これはユーザー要求(「物理シミュレーションのみのCG弾道ではなく実際に検出・追跡した軌跡データを使う」)を、精度的に無理のない範囲で満たす落とし所です。UIでも「実測区間」と「推定(シミュレーション)区間」を視覚的に区別することを推奨します。

## 前提要件(ヒアリング済み)

- Flutter製、まずはiOSのみ対応(Androidは将来対応)
- カメラは「後方固定(ダウンザライン)」で撮影、通常の30fps
- ボール・スイングの画像解析は既存MLパッケージを活用(ゼロからCVモデルを自作しない)
- 飛距離推定はボール実寸(直径約42.7mm)のみを基準にした単眼カメラでの動画解析
- 弾道は動画から実際にボールを画像追跡した軌跡データを使用
- 撮影履歴は不要、単発の「撮影→解析→結果表示」フローのみ

## 1. カメラ撮影

**推奨パッケージ**: `camera`(Flutter公式、`camera_avfoundation`がiOS実装バックエンド)

- `camera` 0.11.x以降、`CameraController`のコンストラクタ(または`CameraController.withSettings` / `MediaSettings`)で**fps・video bitrate・audio bitrateを明示指定できる**ようになっており、30fps固定での録画設定は標準APIでカバーできる。
- プレビュー表示・録画開始/停止・ファイル保存(`XFile`として一時ディレクトリに書き出し→`path_provider`で永続化)はcameraパッケージの基本機能でそのまま実現可能。iOS 10+対応。
- **注意点**: `startImageStream`(フレームバッファのリアルタイム取得)と`startVideoRecording`を**同時に**呼ぶのはiOSで既知の不安定挙動(非mainスレッドでのFlutter engine API呼び出しによるクラッシュ等)が報告されている(flutter/flutter #150005)。「録画しながらリアルタイム解析」は避け、**録画完了→ファイルからフレーム抽出→解析**という逐次処理にするのがMVPでは安全。
- モーションブラー対策として、`AVCaptureDevice.setExposureModeCustom(duration:iso:)`でシャッター速度(露光時間)のみを短く(例: 1/500〜1/1000秒)固定しつつフレームレートは30fpsを維持する、というカスタム露出制御はAVFoundationレベルでは可能。ただしcameraパッケージの公開APIには露出時間の直接指定がないため、**この部分は薄いネイティブ(Swift)拡張が必要**。

## 2. ボール検出・追跡のアプローチ

### 2-1. 検討した選択肢の評価

| 手法 | 評価 |
|---|---|
| **ML Kit Object Detection(汎用/事前学習済みのみ)** | ML Kitの標準オンデバイス検出器はカテゴリが粗く「ボール」自体を識別できない。COCO学習済みの汎用検出器でも「sports ball」は近接画像中心で、芝上の遠く小さい白球への汎化は期待薄。**非推奨**。 |
| **ML Kit + カスタムTFLiteモデル** | `LocalObjectDetectorOptions`でカスタム.tfliteを指定可能。ただしこのカスタムモデル差し替えは基本的に「ML Kit組み込みの汎用saliency検出器が出した領域候補」を**分類**する用途向けで、独自モデルがEnd-to-Endでbboxを直接回帰する構成には向いていない。小さく背景に埋もれるボールは、そもそもsaliency検出器の候補にすら上がらないリスクがある。 |
| **`tflite_flutter` + 自前YOLO変換モデル** | 技術的に可能。ただし2025年8月のTensorFlow 2.20でtf.liteモジュールが非推奨化され、後継のLiteRTへの移行が進行中。前処理・後処理(NMS)をDart側で自前実装する必要があり実装コストが高い。 |
| **`ultralytics_yolo`(Ultralytics公式Flutterプラグイン)** | **推奨。** iOS上ではUltralytics製のSwiftパッケージ(CoreML)をネイティブに使い、単一画像推論APIを提供、リアルタイムだけでなくオフライン単発画像推論にも対応。前処理・NMS・トラッキング(ByteTrack系の`track`タスク)まで内包されており自前実装が最小限で済む。CoreMLはiOSのNeural Engineを活用でき速度面でも有利。 |
| **色/形状ベースの古典的CV(Hough円検出)** | `opencv_dart`(dart:ffi経由のOpenCV4バインディング)で実装可能。芝の上の白い球という条件は色閾値処理と相性が良い一方、影・他の白い物体・モーションブラーで誤検出率が高い。**YOLO系検出のフォールバック/補助**として使うのが現実的位置づけ。単独の主手法としては非推奨。 |

### 2-2. モデルの入手方法

Roboflow Universe上に公開済みのゴルフボール検出データセット・学習済みモデルが複数存在する(例: mAP@50 86.6%程度)。学習済み重みをCoreML/TFLite形式にエクスポートして利用でき、「既存モデルの重みを自分のデータで微調整する」形であれば要求方針(既存MLパッケージ活用、ゼロからモデル自作しない)に整合する。ただし撮影条件(角度・照明・背景)が本アプリと異なる可能性が高く、**実機収録した自前動画数十〜百本程度での追加ファインチューニングはほぼ必須**。

### 2-3. フレーム抽出の方法

`video_thumbnail`は連番フレーム取得には非効率。`ffmpeg_kit_flutter`は2025年に開発終了・バイナリ削除された廃止パッケージであり新規採用は避けるべき。

**推奨**: 薄いネイティブSwiftプラグイン(Pigeon)を自作し、`AVAssetReader`で動画を順次デコードして各フレームを書き出す。

### 2-4. 現実的な精度評価

- アドレス時(静止球): 高精度な検出・ピクセル径測定が期待できる
- インパクト後0.2〜0.5秒程度: ある程度の検出は可能だが、モーションブラーによりbboxの精度は大きく劣化。露光時間短縮のネイティブ制御が実質必須
- それ以降: 検出率は大きく低下し、実用上ほぼ追跡不可能と想定すべき
- 誤検出対策として時系列上の連続性チェック(簡易カルマンフィルタ等)が必須

## 3. 距離推定ロジック

### 3-1. カメラ内部パラメータの取得

録画開始時に`AVCaptureDevice.activeFormat.videoFieldOfView`(水平画角)を取得し、動画の横解像度`W`からピンホールモデルの焦点距離(ピクセル単位)を算出:

```
f_px = (W / 2) / tan(videoFieldOfView_rad / 2)
```

### 3-2. 各フレームでの3D位置推定

ボール実直径 `D = 0.0427 m`、フレーム`i`での検出ピクセル径`d_px[i]`、ボール中心`(u_i, v_i)`として:

```
Z_i = f_px * D / d_px[i]
X_i = (u_i - cx) * Z_i / f_px
Y_i = (v_i - cy) * Z_i / f_px
```

### 3-3. 初速・打ち出し角・方向の算出

インパクト直後の複数フレームのX(t), Y(t), Z(t)に最小二乗フィッティングし、傾きから初速ベクトルを推定:

```
V0 = sqrt(Vd² + Vl² + Vv²)
θ (打ち出し角) = atan2(Vv, Vd)
φ (打ち出し方向) = atan2(Vl, Vd)
```

### 3-4. 弾道物理モデル

空気抵抗を無視した単純放物線は過大評価になるため使うべきではない。抗力+マグヌス揚力を含む運動方程式を数値積分(RK4等)。バックスピン量は実測できないため、打ち出し角等からヒューリスティックに仮定する。結果は「推定飛距離(参考値)」であることをUI上明示する。

## 4. 弾道の表示方法

1. **動画オーバーレイ表示**(メイン): `video_player`で再生しつつ`CustomPainter`でボール軌跡を描画。実測区間は実線、物理モデル延長区間は破線で区別。
2. **俯瞰/側面の模式図**(補助): `fl_chart`の`LineChart`で実測点とシミュレーション曲線を重ね描き。

## 7. 技術的リスク・精度限界(まとめ)

1. **30fpsのモーションブラー(最大のリスク)**: インパクト直後が最も重要かつ最も検出困難な区間。露光時間短縮のネイティブ実装なしでは実用精度が出ない可能性が高い。
2. **単眼カメラでの距離推定誤差**: ボール検出のbboxが数ピクセルずれるだけで距離推定が大きく変動する。
3. **スピン情報の欠如**: バックスピン・サイドスピンを実測できないため、キャリー飛距離はヒューリスティックな仮定を含む「推定値」にとどまる。
4. **誤検出ノイズ**: 白い帽子・雲・反射などによる誤検出。時系列ゲーティング/簡易トラッキングフィルタが必須。
5. **モデル転移学習の必要性**: 公開済みモデルはそのままでは撮影条件にフィットしない可能性が高く、自前データでの追加学習が事実上必須。

これらを踏まえ、**「レーダー式ローンチモニター相当の精度」を目指すプロダクトではなく、「動画解析による目安値+実際に検出した軌跡の可視化」を提供するエンタメ/練習補助アプリ**として期待値を設定するのが妥当。

## 8. フル実装のステップ案(参考)

1. カメラ撮影(固定30fps、録画→ファイル保存)のみをまず動かす
2. 汎用の事前学習済みYOLOモデルでボール検出パイプライン(フレーム抽出→推論→bbox取得)を通す(精度は度外視、配線確認が目的)
3. アドレス時静止フレームでの距離推定式の単体検証(既知の距離にボールを置いた実験で誤差を測定)
4. インパクト後数フレームの検出→初速・角度算出→簡易物理モデルでのキャリー距離算出まで通す
5. 結果画面での動画オーバーレイ表示(CustomPainter)
6. 公開データセットでのファインチューニングモデルに差し替え、実機収録データで精度検証・調整

## 9. 検証方法

- **距離推定式の単体検証**: 実機のiPhoneで、既知の距離(3m, 5m, 10m等)にゴルフボールを置いて撮影し、`f_px`から算出した推定距離と実測値を比較。
- **モーションブラー対策の検証**: 屋外の練習場で撮影し、露出時間を変えて検出成功率をログ出力で比較。
- **エンドツーエンド検証**: レーダー式ローンチモニター(Rapsodo等)や他アプリと並行計測し、物理モデルのパラメータを調整。
- **iOS実機テスト**: Simulatorはカメラハードウェアにアクセスできないため、カメラ・ML推論の実挙動確認は必ず実機(iPhone)で行う。
