# 調査報告: カスタムモデル差し替え後も解析中画面から遷移しない(続報)

- 調査日: 2026-08-25〜2026-08-26
- 対象ブランチ: main
- 前提: [investigation-analyzing-screen-stuck.md](investigation-analyzing-screen-stuck.md)(2026-08-24)で「COCO汎用モデルの精度不足」と結論した問題を受け、[roboflow-model-investigation-guide.md](roboflow-model-investigation-guide.md)の調査に基づきgolf-ball-detection-r3lqjデータセットでファインチューニングしたカスタムモデル(`assets/models/best.mlpackage.zip`)に差し替え済み([model-provenance.md](model-provenance.md)参照)
- 検証環境: iOS Simulator / 実機(いずれも同一症状で再現)
- 使用動画: `IMG_3090.MOV`(1080x1920、8.93秒、約30fps。打ちっぱなし練習場でのスイングを後方から撮影)

## 1. 事象

カスタムモデルへの差し替え後も、解析実行後に「解析中」画面から遷移せず、最終的に以下の例外でエラー表示になる。

```
解析に失敗しました: InsufficientTrajectoryDataException: 飛球区間の観測が不足しています(ボールをロストした可能性があります)
```

旧モデルでは動画全体で検出数1〜2件だったのに対し、カスタムモデルでは検出数が9件程度に改善していたが、症状自体は解消していなかった。

## 2. 調査方法

`lib/domain/services/ball_trajectory_analysis_service.dart`のメインループと`lib/data/ml/ball_detector.dart`に、フレームごとの生の検出結果(信頼度・クラス名・座標・バイトサイズ)とトラッカーの状態遷移を出力する一時的な診断ログ(`[diag]`/`[diag-raw]`)を追加し、実機で取得したログを分析した。加えて、疑わしい時間帯については`ffmpeg`/`sips`で動画から直接フレームを切り出し、目視で実際の映像を確認した。

## 3. 調査の経緯(仮説の変遷)

### 3.1 仮説: iOS Simulatorの速度・CoreML制約が原因(棄却)

シミュレータではCore MLがNeural Engineを使えずCPU実行になるため遅いのではと想定したが、**実機でも同一のエラーが再現**したため棄却。

### 3.2 仮説: 動画フレーム抽出自体が壊れている(棄却)

診断ログでフレームごとのバイトサイズ(JPEG)を出力したところ、699KB〜742KBの範囲で自然に変動しており、黒画像や固定画像が返っているわけではないことを確認した。フレーム抽出自体は正常。

### 3.3 仮説: `ultralytics_yolo`プラグインのYOLO26 end-to-end出力パースの既知不具合(調査したが直接の原因ではないと判断)

GitHub Issue [ultralytics/yolo-flutter-app#487](https://github.com/ultralytics/yolo-flutter-app/issues/487)で、YOLO26のCore MLモデル(`end2end=True, nms=False`、まさに本アプリの`best.export(format="coreml", imgsz=640)`と同じ設定)をiOS側プラグインが正しくパースできず空/デタラメな結果を返す不具合が報告されていたことが判明。修正は`ultralytics_yolo` v0.3.5(PR [#489](https://github.com/ultralytics/yolo-flutter-app/pull/489))で取り込まれ、本プロジェクトの`ultralytics_yolo: ^0.6.13`は`ios/Podfile.lock`上で`yolo-ios-app` v8.9.13(2026-07-28リリース、当該修正および関連の追加修正[#303](https://github.com/ultralytics/yolo-ios-app/pull/303)を含む)にピン留めされていることを確認した。実際にネイティブソース(`ObjectDetector.swift`)を該当コミット時点で取得して読んだところ、end-to-end出力(`[1, max_det, 6]`形式)を正しく処理するロジックが実装済みであることを確認したため、この既知不具合が直接の原因ではないと判断した。

### 3.4 仮説: フルフレーム探索ではボールが小さすぎて検出できない(確認・要因の一つ)

ROIクロップを常に無効化してフルフレーム(元解像度)のみで検出させたところ、**動画全体・全フレームで検出数が0**になった。クロップ(240px/160px四方に切り出してから640x640にリサイズ)を使った場合のみ検出できることを確認し、「小さな被写体を検出するにはクロップによる実効解像度の底上げが必須」という設計上の前提が正しいことを裏付けた。

### 3.5 仮説: トラッキング開始点が誤った物体を選んでいる(確認・修正済み)

診断ログで、動画冒頭(t=0ms)の240pxクロップ内に**複数の検出候補**が返っていることが判明した。

```
t=0ms mode=crop c=Offset(353.5, 1004.3) sz=240.0 n=3
  (conf=0.90, pos=Offset(451.3, 971.4), ...)   ← 採用されていた候補
  (conf=0.88, pos=Offset(350.6, 1002.6), ...)  ← ユーザーのタップ位置(353.5, 1004.3)に近い候補
  (conf=0.33, pos=Offset(303.3, 946.3), ...)
```

`BallKalmanTracker.step()`の追跡開始ロジック(`lib/data/tracking/ball_kalman_tracker.dart`)が、候補の中から**信頼度が最も高いものを無条件に採用**していたため、ユーザーがタップして指定した対象ではなく、たまたま信頼度が高かった背景の別物体をロックオンしていた。一度誤った対象を追跡し始めると、その後は存在しない(または一過性の)対象を追い続けるため二度と検出されず、`InsufficientTrajectoryDataException`に至っていた。

### 3.6 仮説: ゲーティングがサイズの妥当性を見ておらず、近くの小さなノイズに乗り移る(確認・修正済み)

3.5の修正後、実機で再検証したところアドレス区間の追跡は大幅に改善したが、追跡開始から数秒後に**直径5px程度の小さな誤検出(ノイズ状の物体)**に乗り移り、そのまま追跡が固定されて動かなくなる新たな問題が見つかった。`BallKalmanTracker.step()`の候補マッチングが、予測位置からの**距離のみ**でゲーティングしており、対象物のサイズ(直径)の妥当性を見ていなかったことが原因。

### 3.7 実際の映像確認による最終確認: インパクト時のクラブによる遮蔽 + 飛球後の速度が原因

3.5・3.6の修正後も同様のエラーが発生したため、`ffmpeg`で動画から直接フレームを切り出し目視確認したところ、以下が判明した。

- この動画は**録画開始からわずか0.3〜0.4秒でインパクトに達する**、非常にタイトなタイミングで撮影されていた
- t=0〜231ms: ボールは静止しており、修正後のトラッカーは正しく追跡できていた
- t=231ms〜330ms: ダウンスイングのクラブがボールに接近・接触
- t=429ms: クラブがボールの位置に完全に被さっている(インパクト直後)

診断ログの「ロスト開始時刻(t=264ms)」は、まさにクラブがボールに重なり始めるタイミングと一致していた。クラブによる視覚的な遮蔽でモデルの信頼度が閾値を下回り、その直後にボールは秒速数十mで飛び出すため、次の33ms後のフレームでは160pxクロップは言うまでもなく、フルフレーム探索でも(3.4で確認済みの通り)再検出できない。

## 4. 根本原因の特定(まとめ)

今回の症状は、単一の原因ではなく以下3つの要因が重なって発生していた。

1. **(修正済み)** 追跡開始点の選定が信頼度優先で、ユーザー指定位置を無視していた → 背景の別物体を誤ってロックオンすることがあった
2. **(修正済み)** ゲーティングがサイズの妥当性を見ておらず、近くの小さなノイズに乗り移ることがあった
3. **(未解決・設計上の限界)** インパクト前後でクラブがボールを視覚的に遮蔽し、かつボールが秒速数十mで飛び出すため、33ms間隔・160pxクロップという現在の検出方式では飛球区間の観測を安定して得られない

要因1・2は明確なバグであり修正したが、要因3は「30fpsの動画をフレームごとに検出・追跡する」という現在のアプローチ自体の限界であり、コード修正だけでは解決しない。

## 5. 実施した修正

| ファイル | 内容 |
|---|---|
| `lib/data/tracking/ball_kalman_tracker.dart` | `step()`/`track()`に`referencePositionPx`(ユーザーのタップ位置)を追加。指定時は信頼度でなく最近傍の候補を追跡開始点に採用 |
| `lib/data/tracking/ball_kalman_tracker.dart` | マッチング候補のゲーティングに、直前の追跡対象との直径比によるサイズチェックを追加 |
| `lib/core/tracking_constants.dart` | `minDiameterRatio`(0.4)・`maxDiameterRatio`(2.5)を追加 |
| `lib/domain/services/ball_trajectory_analysis_service.dart` | `buildShotResult`に`initialBallPositionPx`を追加し、`analyze()`から一貫して受け渡すよう変更 |
| `test/data/tracking/ball_kalman_tracker_test.dart` | 上記2件の回帰テストを追加(信頼度でなく参照位置を優先すること、サイズ不整合の候補を除外すること) |

いずれも`fvm flutter test`で既存テストを含め全件成功を確認済み。

## 6. 副次的な発見(未解決・要フォローアップ)

- **`analyze()`が1回の操作で11回繰り返し実行される問題**: ユーザーが「この位置で解析する」ボタンを1回だけ押したケースでも、診断ログ上で動画全体の解析が11回連続で走っていることを確認した(`t=0ms`が11回出現)。原因は未特定。処理時間の無駄・診断ログの見づらさにつながるため、別途調査が必要
- 診断用の一時ログ(`[diag]`/`[diag-raw]`、`ball_trajectory_analysis_service.dart`と`ball_detector.dart`に追加)は本調査のために残置したままになっている。今後の対応方針が固まり次第、削除するかログレベルを下げるかを検討する

## 7. 今後の選択肢(2026-08-26時点、未決定)

要因3(インパクト前後の遮蔽・高速移動)への対応方針をユーザーと相談中。候補:

1. 今回は静止区間(アドレス)の検出精度向上までを成果とし、飛球区間の弾道計算は後続フェーズに先送りする
2. インパクト前後で一時的にクロップを大きく・全体探索への切り替えを早めるヒューリスティックを追加する(ただし飛球速度がモデルの検出能力を超える限り根本解決にはならない)
3. 撮影方法のガイドを追加する(カメラをボールに近づける、打席全体でなくボール周辺にズームして撮影する等)
4. 動画内に写っていた市販の弾道計測器(ローンチモニター)のデータとの役割分担を検討する
